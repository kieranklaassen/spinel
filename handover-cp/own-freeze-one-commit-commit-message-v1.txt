A class's own freeze and frozen?: super is Object's, a box calls them

    class Cart
      def initialize = @items = [1, 2]
      def freeze
        @items.freeze
        super
      end
      def frozen? = super && @items.frozen?
    end
    c = Cart.new
    c.freeze
    p c.frozen?

raised NoMethodError for a missing superclass method at `c.freeze`
where Ruby prints true, and

    class Doc
      def initialize = @sealed = false
      def freeze
        @sealed = true
        self
      end
      def sealed = @sealed
    end
    d = Doc.new
    row = [d, 5]
    row[0].freeze
    p d.sealed

printed false where Ruby prints true. Two faults of one override, fixed
together because each hides the other: through a boxed value the
override was never called, so a freeze ending in `super` ran there by
accident; and a `super` that answers the object types the call for the
object, where the boxed line still made a boxed value.

`super` in a freeze or frozen? override that no ancestor defines had no
method to reach, and was typed unknown, so `def frozen? = super` did
not compile. It is now Object's, for an object of the class: freeze
sets the frozen bit of the object's header and answers the object,
frozen? reads the bit, as the call does on a class with no freeze of
its own. It is taken only where the super hands nothing on (a bare
super in a method with no parameters, or `super()`) and carries no
block. A class whose freeze reaches Object's this way is marked as one
whose instances are frozen, as a bare `freeze` in one of its methods
marks it: a write to an instance variable of the frozen object raises
FrozenError however the override was called (by name, an alias, send).

Through a boxed value the builtin freeze ran whatever class the value
had, and frozen? read the header's bit and never asked the class. Both
arms now stand down in a program where a class defines the name, as
the nil? arm above the freeze line and the dup and clone arm below the
frozen? line do (user_defines_or_reads). The call goes on to the
dispatch on the value's class: the class's method runs for its
objects, and every other value comes back to the same builtin arm.

They stand down only where that dispatch keeps the builtin in its
default arm (poly_dispatch_keeps_builtin, the test
emit_poly_builtin_default_at makes). A box the analysis types by the
class (`x = cond ? d : none`, nil in `none`) has a slot typed for the
class's answer, and the default arm declines there and raises for nil.
For a freeze that answers the object the arm now stays, where every
class's freeze answers that one type: the builtin's value is taken
back into the slot, nil as its NULL. Elsewhere the builtin line answers
as before, and where the call is typed for the object its value is
taken back the same way: `y = x.freeze` did not compile there.

Not covered, as before: the same super in a reopened builtin class
(String, Object), whose self is the value; one that passes arguments
or a block; an object laid out by value; and, through a box typed by
the class, a freeze that answers something other than the object or
two classes whose freeze answer different types (the builtin runs).
