WHAT IT CURES. An exception OBJECT raised while another exception is handled lost its cause on the way through an
ensure. A raise stages the cause and a rescue's catch puts it on the object; an ensure's landing is no catch. The tip
resumes an exception from an ensure by reading the cause off the object ("An ensure resuming an exception keeps
the cause it was raised with"), so an object that had not been given the cause yet came out with none. On the
tips before that change these programs were right: this is the remainder of the two rows closed as done by master.

THE CUT, AND THE ONE DROPPED. One statement in sp_raise_cls: an object raised takes the staged cause there where it
has none. A first cut gave the cause at the four landings instead (an inline helper beside sp_exc_caught_obj). It
answered the same and was dropped for its cost: on this tip it moved paths that nothing is raised on (clang 1 to 2
instructions a pass through an ensure; gcc and clang 1 a pass through a filter's block). The cut at the raise
touches no inline function and no line of the compiler, so no generated function changes.

lib/spinel_rt.h AND "ADDITIVE ONLY". The hunk adds a four-line comment and one statement on the line of
sp_raise_cls that stages the cause, so that line shows as edited (+5 -1). No name is removed and no signature
changes. What a generated program calls answers differently only where an object is raised with a cause staged
