A boxed != asks the class's own !=

    class Tok
      def !=(o) = true
    end
    xs = [Tok.new, 3]
    p xs[0] != xs[0]    # false; CRuby: true

`x != y` on a boxed x was `!sp_poly_eq(x, y)`: it asked the class's ==
and never its !=. A typed receiver calls the method, so one object
answered one way through a local and another through an Array. A
rescued exception read by a bare rescue did the same: `e != e` was false
for a class whose != says true.

The operator table a boxed receiver's other operators go through
(sp_user_binop_dispatch) has an arm for != now. In a program where a
class has a != of its own a boxed != asks it first (sp_poly_ne_own,
emitted for such a program alone), and `!sp_poly_eq` answers as before
for every other receiver and for an operand the method's parameter does
not take. A raised exception is boxed as an Exception: one of a class
whose != can be asked takes that class's id first.

So the stand-aside of "An exception read out of an Array is == to itself
as the rescued value" narrows. sp_exc_own_ne is set only where an
exception class has a != that a boxed != cannot ask: a class with ivars
(a raised one the runtime built is the base size), a != whose parameter
takes one kind of value, or a != the program never calls (it is not
emitted). Elsewhere the two boxes of one exception are equal, and !=
asks the class.

A program with no != of its own emits the C it did. In one that has
one, a boxed != costs 23 instructions more on an Integer receiver, 26 on
a String and 59 on an object of another class; on an object of the class
it costs 53 fewer.

Not here: an operand the parameter does not take (`x != 3` where !=
reads `o.v`, and the calls the analysis saw passed a Tok) is still
`!sp_poly_eq`; a != that answers a value other than true or false is
read for its truth at a boxed call.
