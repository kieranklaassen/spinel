## What this changes

```ruby
e = [5, 6, 5].each_with_index
p e.uniq { |x| x }
```

```
spinel diff: output-diff
--- stdout (ruby)
+++ stdout (spinel)
@@ -1 +1 @@
-[[5, 0], [6, 1]]
+[5, 6]
```

Cost, by callgrind, instructions a step with gcc and with clang (100,000 steps against 200,000, 8 distinct keys). Each program sizes the answer (`p e.uniq { ... }.size`), so master runs it right. A lone `|x|` over steps of one value stays within 2 instructions of master, or under it: `{ |x| x }` over `a.each` (of 225 and 176), over `s.each_char` (of 1,712 and 1,587) and over `a.each_slice(2)` (of 2,626 and 2,452 a slice), `{ |x| x[0] }` over those slices (of 767 and 756). A lone `|x|` over steps of several values whose block runs no code (`{ |x| x }`: its body is reads of the parameter and literals), in a program that gives no class an `==`, an `eql?`, a `hash` or a `<=>`, has a survivor's Array made of the Enumerator's item when the survivor is pushed, and the step loop is master's: over `each_with_index` 4 fewer and 15 more (of 929 and 885), over a generator that yields two values a step 1 and 25 more (of 1,347 and 1,316), three values 1 and 25 more (of 1,383 and 1,353); at 2,000,000 steps of `each_with_index` the peak resident size is master's 537 MB. Clang's 15 are layout, measured: `sp_yielded_packed`, which master's C calls from one place and clang inlines there, has a second caller in such a program and is called, 17 instructions a step by callgrind's count of that function; over the generator 12 of the 25 are that call and 13 the first values taken beside. Any other lone `|x|` over steps of several values (`{ |x| x + 0 }`) pays for what a survivor is made of, kept ahead of the first step: over `each_with_index` 88 and 104 more (of 971 and 920), over the generator of two values 44 and 49 (of 1,389 and 1,351), of three 84 and 89 (of 1,425 and 1,388), and 583 MB for 537. It is kept ahead and not read when a survivor is pushed, because an Enumerator hands out its own items: a block that calls anything, or an `==` of the program's own, may reach them through another `to_a` while the steps run, and master reads the first values ahead, so `e.uniq { |x| e.to_a[0][0] = 7; x }.map { |v| Array(v)[0] }` is `[5, 6]` on master and must stay so. No call is known to run nothing: the parameter is the step's first value, of any class, and a Hash's `[]` runs its default block. A lone `|*r|` whose body only reads it, and `&:m`, ask a survivor only and stay within 1 instruction of master: `{ |*r| r[0] }` over `each_with_index`, whose every step is a pair (of 1,199 and 1,199), over a generator of two values a step (of 1,856 and 1,872) and over `a.each` (of 531 and 500); `&:abs` over `a.each` (of 603 and 593). A lone `|*r|` whose body may change it (`{ |*r| x = r; x[0] }`) is asked ahead of the block, at every step: 15 and 9 more over that generator (of 1,857 and 1,874), 23 and 26 over `a.each` (of 532 and 502). A block with two parameters, a block with none, no block, and `uniq` on an Array keep their C. Compile time, by instruction count of `spinel -c` on a program of 1,000 and of 2,000 such calls, against master: `{ |x| x }` 3.83% and 8.07% fewer, `{ |*q| q[0] }` 3.28% and 4.89% fewer; over an Array, where the C is master's, the same to 0.03%.

The other way round, over `o = [5, 6, 5, 7].each`, `o.uniq { |*r| r }` prints `[[5], [6], [7]]` for `[5, 6, 7]` and `o.uniq(&:odd?)` prints `[[5], [6]]` for `[5, 6]`.

The `to_a` that stands in front of a block iterator over an Enumerator hands each item as the block binds it (`enum_hop_yield_view`): the first value a step yields for a lone `|x|`, all of them for a lone `|*r|` or `&:m`. That is right for `map` or `count`, whose answer is the block's. `uniq` answers the items, and got what the block binds in their place.

`emit_poly_uniq_block` now reads the Enumerator itself under such a view. For a lone `|x|` the block binds the first values, as before, and a step that packed two values or more has a new Array of its values for its survivor, made when the survivor is pushed. Where the block runs no code (its body is reads of the parameter and Integer, Float, Symbol, nil, true or false literals) and the program as written gives no class an `==`, an `eql?`, a `hash` or a `<=>`, nothing of the program's runs between the first step and the last push, so that Array is made of the item itself: an Enumerator that keeps its items is read by the view's own `to_a` and the item taken from the Enumerator; one that makes them anew at every `to_a` (a generator) is read once, plain, with the first values taken beside. For any other block it takes the Enumerator's plain `to_a` and puts the first values in place, ahead of the first step, as the view's `to_a` does, and keeps the values after the first of each such step, one step's after another's, taken ahead of the first step too; the survivor's Array is made of those. For a lone `|*r|` or `&:m` the view's `to_a` stands as it did, a new Array of each step's values, and that Array is the survivor, as on master, but for a step of one value nothing can change in place (an Integer, a Float, a Symbol, nil, true or false): that value is the step's survivor. Whether a step is one is asked of a survivor only, when it is pushed, where the block leaves its Array as it is: its body uses the parameter only as the receiver of an index that is not assigned, of `size`, `length`, `first` or `last`, each of them the builtin's (the program gives no class a method of that name), which is all the body written for `&:m` does. Any other block may change its Array (`{ |*q| k = q[0]; q.pop; k }`), so there the value is taken ahead of the block. Any other one value keeps its Array for the survivor: it may be a String or an Array the Enumerator made and keeps (`each_char`, `each_slice`), and what `uniq` answers must not be an object the Enumerator's next `to_a` hands out again. So the Array a step packed is never the survivor either: the survivor is a new one of the same values. An Enumerator whose steps yield one value or several (`Enumerator.new { |y| y.yield 1; y.yield 2, 3 }`) comes out right by the same road. It does so only where the program as written gives no class a `uniq` of its own (master's `an_prog_never_gives`): no `def` and no Symbol of that name, and no site where a method is named, made or loaded by something the text does not spell. A `uniq` the program gives Enumerable or Enumerator, in a file the compiler reads or in one it does not, answers what it likes, so such a program keeps master's C.

A step that yields one value has the parameter for its item, and a block may change that String in place: over `"a\nb\na\n".each_line`, `e.uniq { |x| x.chomp!; x }` answers `["a", "b"]`, on master too, for `x.chomp!` rebinds the parameter and `uniq` kept the changed one. So for a lone `|x|` the survivor of such a step is the parameter as it is after the block ran, as it was; a step that packed several values has the new Array of them.

Not in this change, and still wrong as on master, each left for a change of its own. A program that holds a `def` or a Symbol named `uniq`, or a site of the five kinds master's `an_prog_never_gives` lists (`5.send(m)`, `[1].map(&pr)` with a proc in a local, a file the compiler does not read, a module mixed in), still prints `[5, 6]` for the two lines above: so after `require "json"`, whose text holds the word `require` in a string or in a comment, and after `require "set"`, whose text mixes a module in, and not after `require "time"`. The chain written in one expression, `[5, 6, 5].each_with_index.uniq { |x| x }`, is refused on master and here (unsupported call). Under a lone `|*r|` or `&:m` a step of one value that is a String, an Array, an object or an Integer past 64 bits still has its Array for the survivor: `%w[a b a].each.uniq { |*r| r[0] }` is `["a", "b"]`, and master and this print `[["a"], ["b"]]`; so over `each_char` and `each_line`, over the `each` of an Array of Arrays, and over an `each_slice` or an `each_cons` held in a local. A step of no value: over `Enumerator.new { |y| y.yield; y.yield(nil) }`, `g.uniq { |*r| r.size }` is `[nil, nil]`; master prints `[[], [nil]]`, this `[[], nil]`. A block that changes its `|*r|` over steps of several values has the changed Array for the survivor: over `e`, `e.uniq { |*r| r << 1; r[0] }` is `[[5, 0], [6, 1]]`, and master and this print `[[5, 0, 1], [6, 1, 1]]`. A lone `|x|` over a Hash's `each` has the pair for its one value, so the survivor is the Array the Enumerator keeps. A block that changes in place the first value of a step that yields several: over `w = [+"a\n", +"b\n", +"a\n"].each_with_index`, `w.uniq { |x| x.chomp!; x }` is `[["a", 0], ["b", 1]]`; master prints `["a", "b"]`, this prints `[["a\n", 0], ["b\n", 1]]`.
