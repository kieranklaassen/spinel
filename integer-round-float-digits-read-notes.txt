WHY IT EXISTS

`make gate` on darwin-arm64 fails on master 7232a8021 (the Mac's run, not mine; I have no arm64 machine) in ruby/spec's core/integer, round_spec__004: `42.round(Float::INFINITY)`, `42.round(-Float::INFINITY)` and `42.round(Float::NAN)` print 42 there, where CRuby raises RangeError "float Inf out of range of integer", "float -Inf ...", "float NaN ...". The cause is one cast. emit_int_expr writes a typed Float in an Integer slot as `(sp_int)(X)` (src/codegen.c, the Float arm of emit_int_expr_ex), and C leaves that cast undefined for an infinity, a NaN and a Float past the word. x86-64's instruction gives the smallest Integer; arm64's saturates and gives 0 for a NaN; a compiler that folds the cast of a constant gives anything (clang 18 on x86-64 prints 42 for the three lines, here, on the bare tip this head is cut on).

WHAT IS TAKEN: the digit count of round, floor, ceil and truncate, at every site where it is read through that cast and CRuby reads it by NUM2INT. Nine sites:

  A1  Integer receiver, one argument (int_arms_round_divide): `sp_int_NAME(r, COUNT)`, all four names.
  A2  Integer receiver, a count and `half:` (the same function): round only.
  B1  Bignum receiver, truncate (emit_call_bigint_arms).
  B2  Bignum receiver, round, ceil, floor (the same function).
  C1  Float receiver, round with a `half:` read at run time (emit_scalar_recv_arms).
  C2  Float receiver, a count that is not an Integer literal, all four names (the same function; a literal `half:` mode ends here too).
  E1  a receiver in a boxed slot, round with `half:` (emit_poly_numeric_call).
  E2  a receiver in a boxed slot, one argument, all four names (the same function).
  F   a receiver in a boxed slot where a class of the program defines the method (emit_poly_defaults_n, src/codegen_poly_plan.c): its own `(sp_int)_tN` of a count hoisted as a Float.

WHAT IS NOT, each for its reason (all recorded as side finds, none taken):
  - emit_int_expr itself. The cast serves every Integer slot a typed Float reaches (an index, a repeat count, a width). CRuby raises the same RangeError in most of them, but that is every program with a Float in an Integer slot, and its cost. This piece changes no C outside a digit count.
  - floor, ceil, truncate with `half:` and a count (Integer, Float and boxed receivers): CRuby raises the arity's ArgumentError before it reads the count; the count is bound, cast and never used. Master's C stays (the binder is called with fdig 0).
  - Rational#round and kin (the Rational arms of src/codegen_call_numeric.c): a Float count is CRuby's TypeError "not an integer" whatever its value. Another cause: the count's class is not checked.
  - a count held in a boxed slot: sp_poly_arg_int_chk in the runtime; an infinity raises there with other words ("float out of Integer range (Bignum promotion pending)"), a NaN is cast (sp_float_fit_i's comparison is false for a NaN).
  - a count past a C int with floor, ceil, truncate and with a Float receiver: no check of the int range (`1234.floor(1e10)` answers 1234, `1234.floor(2 ** 40)` 1234, `1234.5.round(1e10)` 1234.5; CRuby raises "integer 10000000000 too big to convert to 'int'"). Whatever the count's class.

HOW TO READ IT

1. float_ndigits (src/codegen.c) is the one question: would emit_int_expr write this count as the cast? It is emit_int_expr_ex's own path to its Float arm: the count is typed Float, is no splat, is not a boxed yield value, is not widened to a Bignum. Anything else is "no" and the site emits master's text. A FloatNode whose value a 32-bit word holds is "no" too: master's cast of that constant is defined and right, so its C stays. The type is asked first, so a count that is no Float costs one comp_ntype.
2. sp_float_to_ndigits (lib/spinel_rt.h, beside sp_float_fit_i) is `static inline`: the range test and the cast. In range it is the cast master made, so every answer master got from a Float inside the word is the same answer. Out of range it calls the cold sp_float_ndigits_range, which raises with CRuby's words: "float %.10g out of range of integer" for a finite Float (CRuby's own format), "Inf", "-Inf", "NaN" for the others. The test is written so a NaN fails it. (double)INTPTR_MIN is exact at either width.
3. Where the count is converted. CRuby converts it inside the method, after the receiver and every argument have run. So:
   - A1, E2: master's raise (round's check of the count) was inside the callee, after both C arguments. The conversion is now an argument, and C does not order arguments: the receiver is read into a temp first (E2: hold_operand, rooted as E1's is). Only for a Float count; any other count has master's text.
   - A2, C1, E1: the count is bound ahead of the keywords' values. A Float count is bound as the Float it is (emit_ndigits_bind) and converted in the call's argument (emit_ndigits_use), after the keyword binds.
   - C2: master binds the count, then reads the receiver. A Float count is bound as a Float, the receiver read, then the count converted into the temp the rest of the arm uses.
   - B1, B2: master's own check of the count already stands in the argument (`({ sp_int _rnd = COUNT; sp_int_round_check_ndigits(_rnd); _rnd; })`); the conversion stands in the same place. So with gcc a Bignum receiver that prints is still run after the count has raised, as on master for a count past a C int (probe a8, b1).
   - F: the arguments are hoisted ahead of the dispatch; the conversion stands where the cast stood.
4. The two probes every reader runs. A receiver held ahead of arguments that change it: A1 and E2 now hold it (b1: `n.round((n = 5; b))` and `v.round((v = 6; b))` are CRuby's 1230; the bare tip answers 10 with gcc). A receiver read after arguments newly run: C2 reads the Float receiver after the count, as master does (b1: `f.round((f = 2.5; a))` is 2.5 on both, CRuby 1234.6), and B2 as above. Neither is made by this piece; no cell is lost.
