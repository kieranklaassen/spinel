A proc in a local that held nil first reads the argument it is given

    h = nil
    h = ->(x) { x * 2 }
    p h.call(1.5)

printed 0, and with `->(s) { s.length }` called on "wxyz" it raised
NoMethodError for an Integer. A local that holds nil as well as the
proc is a boxed slot, and the site loop of infer_block_params types a
literal's parameters only for a receiver it knows as a Proc. The
parameters kept the Integer default and read the argument's word
through it. The same literal in a local written once was right.

The loop now takes such a local too, and cs_type_proc_site an arm of a
conditional the local is written with (`f = on ? ->(s) { ... } : nil`),
where the proc stays with its name: every read of the local is the
receiver of call, (), yield, ===, nil? or !, or a condition, and no
write of it is the value of something else. The calls through the name
are then all the calls there are.

A proc that is copied to a second local, stored, answered or handed to
a method is called from where no call through the name shows, and
keeps master's C; so does one called as `f[x]`, which on a boxed
receiver is an index. A callback called with Integers keeps master's
C too.

One cost. A callback fed its own result (`t = f.call(t)`) is handed a
boxed value, so its parameter is boxed. With `s + "!"` that raised
TypeError on master and with `s * 1.5` it printed 6.0 for 6.75; with
`s + 1`, which was right, a call is now 113 instructions against 74
(callgrind). The call site is the same in the three, so the right one
cannot be left out.

The guard walks its own parent map from the program's root. The
rewrite of `g = (f = x)` points g's write at f's and leaves the
parentheses behind, still naming f's write, and an_parent_map, which
takes the last node that names a child, answered with them: f's write
looked like a statement.
