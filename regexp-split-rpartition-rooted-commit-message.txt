split and rpartition with a Regexp keep their pieces across a collection

    rows = []
    20_000.times do |i|
      line = "id" + i.to_s + "\tname" + i.to_s + "\t" + (i * 3).to_s
      rows << line.split(/\t/)
    end
    bad = 0
    rows.each_with_index { |r, i| bad += 1 unless r[0] == "id" + i.to_s }
    p bad

prints 2 in a plain run where CRuby prints 0: two kept rows hold
another row's fields. 8 rounds of s.split(/ /) on an 800 KB String
exit 139, and on a 6 KB String 20,000 rounds of rpartition(/b/) answer
a freed head or match 113 times.

sp_re_split_limit kept the Array it fills in a C local with no root, so
the collection that a later piece's allocation starts freed the Array.
sp_re_rpartition rooted its Array but made the head, the match and the
tail before it pushed any of them, so the head and the match had no
holder while the next piece was allocated.

split now roots its Array where it is made, as scan does, and
rpartition pushes each piece as it is made, as partition with a String
does. The root costs split 20 to 24 instructions a call (callgrind,
200,000 calls: "ab cd ef".split(/ /) goes from 1,283 to 1,303 a call, a
subject with no match from 545 to 569); rpartition's count does not
rise.

Test: test/regexp_split_rpartition_rooted.rb, in GC_STRESS_TESTS.
Without the change it exits 139 in a plain run and aborts at level 2.
The generated C does not change.
