A nil stored where Strings are changed in place stays nil

    def pick(i) = i == 0 ? "pa".dup : nil
    z = [pick(0), pick(1)]
    z[0] << "!"
    p z                 # ["pa!", nil]

died with a segmentation fault. `z[1].nil?` answered false, `z.compact`
kept the element, and `z.each { |e| e << "?" if e }` raised
NoMethodError.

An element that is changed in place is stored as a String handle, and a
value that is not a handle yet is wrapped in a fresh one where it is
stored. sp_String_new_shared hands a nil back as NULL, and the store
boxed that NULL with sp_box_obj: a String handle around nothing, which
no reader takes for nil.

The store now tests the value before it wraps it and boxes a nil as
nil. The other arms of emit_boxed_strbuf and emit_str_array_handles
make that test after the wrap, with sp_box_nullable_obj; made before
it, the C compiler drops the test sp_String_new_shared makes itself.

A value that is never nil keeps the C it had. The list is the one an
instance variable's nil-ness is decided by (ivs_never_nil): a literal,
an interpolation, a sign on a String literal, an operator or to_s on a
builtin receiver. nil.dup is nil, so a dup is taken as never nil only
where its receiver is.

That leaves the values that can be nil: a call that answers a String
or nil, a slice past the end, an element or a Hash value that is not
there, `find`, `&.`, a bang method that changed nothing, a call found
at run time; and the calls the list does not know, which pay the test.
