    class Tagged < StandardError; attr_accessor :tag, :at; end
    kept = []
    60.times do |i|
      s = +"m"
      s << i.to_s
      begin
        raise Tagged, s
      rescue Tagged => e
        e.tag = "tag-#{i}"
        e.at = [i, "a#{i}"]
        kept << e
      end
    end
    # --share-strings: 59 of the 60 read back wrong; CRuby: none

A class of the program's under a builtin exception, with ivars and no
initialize in its chain, has no constructor on its path, so the runtime
builds it. With --share-strings a raise whose message is a String the
program appends to builds the exception at the raise, to hold that
String, and builds it as a plain exception of the base size: the arm
typed to the class wrote its ivars past the end, in a plain run.

Without the flag the same class was written past its end once an arm
that names no class of the program had caught it. sp_exc_new_for_catch
built it at the base size there too, and a method of the class called
on the kept value stored its ivars beyond the object:

    class Marked < StandardError

      begin

An arm typed to its parent, where the parent is such a class too, built
it at the parent's size, and the ivars the subclass adds were written
past that.

A begin with an ensure holds an exception that leaves through its
rescue clauses, raised in a clause or matched by none, as its object
until the ensure has run, and built it with sp_exc_new_for_catch too.
Raised in a clause and caught afterwards by an arm typed to the class,
29 of 30 read back wrong, without the flag.

An ensure with no rescue clause, a begin's or a method's, makes the
object of a raise that passes through it and holds it for the raise
after its body, with that function again, and the arm typed to the
class takes what it is handed:

Built by `.new`, or by the rescue that catches a raise by its name, it
had its own size, but sp_exc_new_sub_sized gave it the base exception's
scan:

    class ParseError < StandardError; attr_accessor :line, :ctx; end
    rows = ->(n) { (0...n).map { |i| [i, "r#{i}"] } }
    e = ParseError.new("m")
    e.ctx = rows.(3)
    20000.times { rows.(3) }
    p e.ctx           # [1, "r1"]; CRuby: the three rows

An ivar the program stored was never marked, and its value was freed
under the exception in a plain run.

One builder cures both. sp_exc_new_sub_ivars takes the class's own
scan. The rescue has to know which class was raised, and all it holds
is the name. The names of these classes stand in one table of the
generated code (sp_xbn_name), and that code passes a class's row where
it raises the class; the rescue then knows the class by one range test
on the pointer (sp_exc_own_by_name), whatever the number of classes and
the length of their names, and sp_user_exc_parent is not asked a second
time. Where sp_exc_new_for_catch, sp_exc_caught_obj or
sp_exc_ensure_obj would build the exception, a program that has such a
class calls an entry of its own generated code in that function's place
(sp_exc_catch_own, sp_exc_caught_own, sp_exc_ensure_own): a test that
hands a row to the program's maker, out of line and cold, and anything
else to the runtime's function, so that the code around the call stays
what it was where nothing is raised. None of the three functions
changes, and a name that is no row is built as it was.

Where sp_exc_new_for_catch built such a class before, a message given
as a frozen literal stays frozen (`e.message.frozen?`,
`e.message << "x"` raising FrozenError): sp_exc_new_sub_caught is the
same builder with that function's own test of the message and its
root of the caller's message. It calls sp_exc_new_sub_ivars and holds
no third copy of the body.

A program without such a class emits the C it did. sp_exc_new_for_catch
does not change, and sp_exc_new_sub_sized stays, with the base scan:
for a class with an initialize of its own, whose C does not change
either, and for such a class whose ivars are all unboxed, where its
size is written, at `.new` and at the arm that names it: it has
nothing for a scan of its own to mark (class_needs_scan) and is built
there as it was. An arm whose class has such a class under it compares
the raised name with its own row first, and asks the table for any
other name. A builtin exception the program reopens is not such a
class.

Not here: an attribute nothing has stored. The struct is zeroed, as it
was, and zero is not nil in every slot: one the compiler types as an
Integer or as a boxed value reads 0 until it is stored, where CRuby
reads nil. `p ParseError.new("m").line` prints 0 before this change
and after it. Where the object was built at the base size that read
went past its end and printed what lay there; it reads the object's own
zeroed slot now, and a program that crashed ahead of such a read
reaches it. Seeding nil is a change of its own: CRuby runs methods of
the program that the compiler does not (a `to_ary` under a multiple
assignment), and where one of them stores a zero the zeroed slot is
CRuby's answer.

Nor whether an attribute was assigned: a zeroed slot of those two
kinds answers a presence read as assigned.
`p ParseError.new("m").instance_variables` prints [:@line, :@ctx]
before this change and after it, where CRuby prints [].

Nor a class read off a value (`raise x.class, "re"`) that an arm naming
no class of the program catches. Its name reaches the raise as a copy
(sp_exc_class_name), which is no row, and the arm still builds it at
the base size; the arm typed to the class builds it as itself, unless
an ensure held it first: the ensure builds it at the base size, as
before this change, and the arm takes that object. And a subclass
caught by an arm typed to a parent that has a method of its own and no
attribute, or by a bare arm typed to the parent, is still built at the
parent's size, as before: ivars a method of the subclass stores go past
the object.
