super in a freeze or frozen? override is Object's

    class Cart
      def initialize = @items = [1, 2]
      def freeze
        @items.freeze
        super
      end
      def frozen? = super && @items.frozen?
    end
    c = Cart.new
    c.freeze
    p c.frozen?

raised NoMethodError for a missing superclass method at `c.freeze`
where Ruby prints true. `super` in a freeze or frozen? override that no
ancestor defines had no method to reach, and was typed unknown, so
`def frozen? = super` did not compile.

It is now Object's, for an object of the class: freeze sets the frozen
bit of the object's header and answers the object, frozen? reads the
bit, as the call does on a class with no freeze of its own. It is taken
only where the super hands nothing on (a bare super in a method with no
parameters, or `super()`) and carries no block.

A class whose freeze reaches Object's this way is marked as one whose
instances are frozen, as a bare `freeze` in one of its methods marks
it: a write to an instance variable of the frozen object raises
FrozenError however the override was called (by name, an alias, send).
A program that never names the override emits the C it did.

Not covered, as before: the same super in a reopened builtin class
(String, Object), whose self is the value; one that passes arguments
or a block; an object laid out by value.
