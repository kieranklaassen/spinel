An operator that asks an object's == or divides by zero runs in its place among a call's operands

    class Seen
      def ==(o) = (puts "eq"; true)
    end
    def lg(n) = (puts "lg#{n}"; n)
    def pair(a, b) = [a, b]
    v = Seen.new
    z = ARGV.size
    p pair(lg(1), 3 == v)    # lg1, eq; spinel with gcc: eq, lg1
    p pair(lg(2), 10 / z)    # lg2, then ZeroDivisionError; spinel with
                             # gcc raised with no lg2

A builtin operator over scalars is no effect: it computes a value and
touches nothing, so the operands of a call are not put in order around
it. call_is_scalar_op asked that of the receiver and of the result
only. `3 == v` has both scalar and asks v's own `==`; a division has
both scalar and raises on a zero divisor. Either one beside an operand
that prints was left to C's order.

call_is_scalar_op also asks that the argument is of a kind that runs
no code of the program's (ty_runs_no_code: numbers, Strings, Symbols
and the like). Every caller asks "can this run code", and for an
object's `==` the answer was wrong for all of them.

The raise is asked only where order is (subtree_has_side_effect): `/`
unless one side is a Float, `%` always, unless the divisor folds to a
number other than zero (`n % 16`, `n / SIZE`). The callers that ask
whether code runs keep a division as it was: a loop that caches a
String's bytes around `h = (h * 31 + s.getbyte(i)) % m` still does.

A constant divisor is folded through fold_int_const_name, which read
the whole node table for the constant's one write each time it was
asked. The order question asks it of every such divisor among a call's
operands, so the write is now kept per name (a CgMemo, dropped when a
constant's write is appended). optcarrot's C is the same and it
compiles in fewer instructions than before: 8,346,448,584 for
8,349,046,980.
