A C function's String argument stays rooted beside an argument that allocates

    module LibC
      ffi_func :strncmp, [:str, :str, :int], :int
    end
    s = +"12"
    t = s
    t << "345"
    p LibC.strncmp(s, t, s.size + 0)

printed 170 at SPINEL_GC_STRESS=2; it is 0. A String held as a handle
goes to a :str argument as a copy when another operand of the call runs
code, and that copy is held by nothing but the C call's argument list:
the second copy's allocation collected the first. A handle beside a
call that builds a String, or beside an Integer argument that allocates
on its way, lost its copy the same way (strncmp(s, joined(x, "345"), 5)
answered -170, with clang 170), and so did the Strings handed to a
variadic function.

emit_call_cmethod_arms rooted the String arguments only where the call
can run Ruby code (a callback, a blocking call). It now roots each
String made where it stands in the call (ffi_str_arg_fresh) when
another argument's evaluation allocates (ffi_str_arg_beside_alloc): in
its temp where the call already takes the temp form, else in a slot the
argument is assigned to in its own place (ffi_arg_hold). No argument
moves, so the arguments run in the order they ran in.

An argument the operand order ran ahead of the call, a read of a value
its owner holds (operand_is_held_read: a typed Array's element, a plain
reader, a Hash's value, a length) and a handle's read that hands C the
live buffer are neither made here nor allocating: those calls keep
their C.
