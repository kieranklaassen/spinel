A zip or combination block in a method that yields is handed its elements

    def each_pair_of(a, b)
      a.zip(b) { |x, y| yield x, y }
    end
    each_pair_of([1, 2], ["a", "b"]) { |n, s| p [n, s] }

printed [nil, nil] twice where CRuby prints [1, "a"] and [2, "b"], and
`def pairs(a) = a.combination(2) { |x, y| yield x + y }` did not build
for an Integer Array. The same with `&blk` and `blk.call`, with the
yield after the loop, in a class's own `each`, and for `permutation`.
Where the block reads its parameters, as in `r << x + y`, the nil
raised NoMethodError.

A method that yields or asks block_given? is spliced into its caller
with its locals renamed (rename_local), and so are the locals of a
parameter's default, which runs at the call. Each is still declared in
its scope under the name it was written with. iter_ewi_zip_poly_arms
asked the scope for the block's parameters by the new name, found
neither, and emitted the loop with no binding at all.
iter_combination_cons_arms and emit_poly_combination_param asked the
same way for the parameter's type, took the miss for a boxed value and
wrote one into an Integer Array's slot.

The five lookups now go through block_param_local, which asks by the
name as written when the new one is not found. Where the first lookup
finds the local the C is what it was.

Not here: handed its elements, the block meets what a zip or
combination block meets at the top level. `x << "!"` changes a copy of
a String element; a method called with an Integer and then a Float
second array prints the Float's bits; and one that yields the pair and
then an element, called with two kinds of array, crashes.

with --enable-frozen-string-literal). master does not build it; section
by section, 9 of its 32 lines are wrong, 11 are in the five sections
that raise NoMethodError and 12 in the three that do not build.
